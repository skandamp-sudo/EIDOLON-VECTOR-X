# Independent evaluation handoff

**Status:** No participant observations or independently authored inventory or ambiguity labels were supplied for this release. Effectiveness on those populations is unmeasured. The included app examples and release checks are engineering fixtures.

## Freeze and collect

Choose the build, target population, tasks, inclusion criteria and scoring rules before seeing outcomes. A reviewer outside implementation authors the cases and a second reviewer adjudicates disagreements. Keep wording, order families and source documents disjoint from development fixtures. Hash the task file and answer key separately before exposing tasks to operators. Record the commit, model identity when applicable, condition order, start/end time and task ID. Preserve failures, abstentions, withdrawn trials and missing optional ratings. Report counts and denominators, with participant- or scenario-level uncertainty when sample sizes permit it.

Obtain consent for local timing and exports. Use anonymous participant codes. Store private forms, keys and exports outside the checkout. Each participant starts with a fresh browser context. Keep raw query text and participant notes out of the release PR.

## Offline scoring

Run `node frontend/score-independent.mjs clarity /path/to/private-cases.json` or use `supply` for inventory. The scorer emits aggregate counts and a file SHA-256. Undefined ratios and absent human outcomes appear as null. It does not certify that the author was independent.

Each UTF-8 file is a JSON array of up to 512 unique cases and at most 1 MB. For **CLARITY**, each case contains `id`, `text` and `spans`. A span contains `kind`, inclusive `start` and exclusive `end`. Supply an empty array for a clear instruction. Use the six cue names displayed by the app. Optionally supply `resolution_correct` from blind adjudication of an actual session. Leave it null when unobserved.

For **SUPPLY**, each case contains `id`, `day`, `events`, and a boolean `reject`. Use the seven event fields shown in the app’s audit log. For a valid stream, `orders` lists every expected order group once, each with `id`, boolean `risk` and `ship` as a simulated day or null. Separate expected rejections from valid operational forecasts. False alarms and missed risks carry different costs, so report their counts alongside averages. Multiple snapshots of the same order are correlated. Keep the family ID in the study ledger when estimating uncertainty.
